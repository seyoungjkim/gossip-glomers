# Notes
Note: This implementation is buggy because writes are not ordered.
The maelstrom checker does not work well for this workload, so I will focus on `txn-list-append` instead.

## Requirements
### Prevent G0 (dirty write)
> A cycle of transactions linked by write-write dependencies. For instance, transaction T1 appends 1 to key x, transaction T2 appends 2 to x, and T1 appends 3 to x again, producing the value [1, 2, 3].
> Or, T1 writes x=1 and y=2, T2 writes x=2 and y=1, and the final result is x=1 and y=1.

`handleTxn` locks for the duration of the transaction, preventing T1 and T2 writes from interfering with each other.

### Prevent G1a (aborted read)
> An aborted transaction T1 writes key x, and a committed transaction T2 reads that write to x.

`handleTxn` aborts only if locks cannot be acquired, and this occurs before the key-value store is updated. So there cannot be dangling writes.

### Prevent G1b (intermediate read)
> A committed transaction T2 reads a value of key x that was generated by transaction T1 other than T1’s final write of x.

`handleTxn` locks for the duration of the transaction, preventing T2 from reading until T1 is done with all writes.
Even if T1 and T2 are on separate nodes, N1 sends T1 to N2 in one request, and N2 will acquire a lock for T1. T2 cannot acquire the lock during this time.

### Prevent G1c (circular information flow)
> A cycle of transactions linked by either write-read or read-write dependencies. For instance, transaction T1 writes x = 1 and reads y = 2, and transaction T2 writes y = 2 and reads x = 1

`handleTxn` acquires exclusive locks for each key being updated, so T2 would not be able to acquire the lock and write y while T1 is reading y.
